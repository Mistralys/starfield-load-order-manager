# New Feature: Load order profiles

Starfield supports playing with different characters, which have separate folders for savegames. 
These characters can (but must not) have different load orders. In fact, my mod manager tool facilitates 
this through the concept of "Profiles". Each profile is a set of mods that is loosely tied to a 
character in Starfield (it is up to the user to select the mod profile matching the character).

This means that the application must support something similar to switch between load orders. 
I think that it makes sense to use the "Profile" terminology as it is already familiar to mod users.

## The Profile System

### Profile folders

All profiles are saved in a `Profiles` subfolder of the configured appdata folder to keep things clean. 
This folder must be created automatically if it does not exist.

Each profile must have its own subfolder in the `Profiles` folder, named after the profile ID (see the section
"Profile properties" on details regarding the profile ID). Using the profile ID means that the folder name 
stays readable to users should they want to edit the profile files manually. This folder must also be created 
automatically if it does not exist. 

> NOTE: This folder can be used in the future to store additional profile-specific data if needed.

### Profile files

The aim of profiles is to maintain a separate state between different load orders. To this end, every profile
subfolder contains the following files (in the order that they must be created):

1. `profile.json`: The profile's properties (see the section "Profile properties").
	- This is created when the profile is created.
	- It is always created first, before any other profile files.
2. `main.txt`: The source used for the `Plugins.txt` file when this profile is active.
	- The source for this file is always the current `Plugins.txt` file in the appdata folder.
	- Created on demand if it does not exist.
3. `reference.txt`: The reference file for this profile, used for change detection and sort order.
	- The source for this file is always the profile's `main.txt` file.
	- Created on demand if it does not exist.

File IO operations on these files must have graceful error handling (aborting the current operation, like 
creating a new profile):

- If the profile folder cannot be created, an error message must be shown.
- If any of the profile files cannot be read or written, an error message must be shown.

### Profile properties

- ID
	- Internal
	- Auto-generated (see section "ID generation") 
- Label
	- Required
	- Editable
	- Max. 30 chars
	- Trim whitespace
	- Must be unique (case-insensitive)
- Description
	- Optional
	- Editable
	- Max 500 chars
	- Trim whitespace

> NOTE: Enforcing these validation rules is done by the create / edit profile UI windows.

#### Disallowed labels

- The following labels are disallowed, as they would conflict with the default profile (case insensitive):
  - `Default`

#### Profile ID generation

The ID should be generated by transliterating the label. The resulting ID must be unique (none of the
existing profiles have the same ID). If a generated ID already exists, a numeric suffix should be appended 
to make it unique (e.g. `my-profile`, `my-profile-1`, `my-profile-2`, etc.), starting at `1` and incrementing
as necessary.

- Character set: ASCII
- Word separator: dashes
- Case: lowercase
- Accented characters: replaced with unaccented equivalents (do not use any external libraries, lossy conversion is acceptable)

### Profiles Storage

Each profile has its own JSON storage file in the profile folder (see the "Profile files" section).
The JSON data should contain the profile properties (see the section "Profile properties"). Other
information (e.g. the profile folder name) can be derived from these properties. A dedicated model 
class should be created to represent profiles in the application.

#### Example profile JSON

```json
{
  "label": "My Character",
  "description": "Main playthrough character"
}
```

> NOTE: The profile ID is not included in the JSON, as the profile folder is the authority for profile IDs.
> Duplicating it in the JSON opens the possibility of the ID getting out of sync with the folder name if
> a user manually changes profiles.

### Discovering Available Profiles

On application startup, all profile subfolders in the `Profiles` folder must be scanned for available 
profiles. A profile is considered valid if its `profile.json` file exists and can be read correctly.
All other folders must be silently ignored.

A collection class should be created as central API to manage the available profiles in the application.

### Active Profile Tracking

The application must track the currently active profile. This information should be stored in the 
application configuration, under the `activeProfileId` key. If no profile has been selected 
specifically or the stored value is invalid, the value should be the default profile ID.

The profile collection API is the ideal place to get and set the active profile.

### Renaming profiles

Changing the label of a profile must also rename the profile folder. The reason is that it contains the 
profile ID, which is derived from the label. In the unlikely event that the target folder name already 
exists (the profile properties window already ensures that it is unique), the rename operation must fail 
gracefully with an error message.

> NOTE: Case-sensitive renames are not an issue, because the folder name (= the profile ID) is always lowercase.

### Default profile

If no profile exists, a virtual "Default" profile is created automatically. If the user only uses a 
single character for their games and do not need profiles at all, they can do everything with only the 
default profile.

- The default profile is virtual: It does not have a `profile.json` file, but otherwise behaves like a normal profile.
- The default profile's properties are immutable:
  - ID: `default`
  - Label: `Default`
  - Description: `The default profile is always available.`
- The default profile cannot be deleted through the application's UI.

#### Creation on demand

The default profile should be created on demand when it is used and any part of it is missing. If needed, use the 
main `Plugins.txt` as source for both the `main.txt` and `reference.txt` (follow the profile file creation logic 
as detailed in the "Profile files" section).

Example scenario: The user deletes the default profile folder while the application is open, and the default profile
is active. On the next change detection cycle, it is detected that the default profile's `reference.txt` is missing.
This causes the entire default profile structure to be verified, and all files to be created automatically.

### Switching profiles

The premise of switching profiles is to maintain the current `Plugins.txt` state, regardless of whether it
is in a dirty state or not. The user can switch back to it anytime to fix issues later, if any. No confirmation
is necessary on switching.

1. The current `Plugins.txt` file is saved to the active profile's `main.txt` file to back it up.
3. The `Plugins.txt` is replaced with the contents of the selected profile's `main.txt` file.
4. The active profile ID in the application configuration is updated.
2. The active profile display in the main window is updated.

> NOTE: Through the active profile ID switch, the periodic change detection automatically uses the new profile's 
> reference file.

## The Profile Management UI

### Active profile display

In the main window, the label of the active profile must be visible, possibly as a text label on the right-hand 
side below the menu. Clicking on it should open the "Switch profile" window.

### Profile menu

Switching and managing profiles should be done via a new "Profile" menu item in the main window's menu strip,
placed between the "File" and "Settings" menus. 

This must have the following sub-items:

- Switch profile > Open profile selection window
- Manage profiles > Open profile management window

### Switch profile window

Window with a card-based view to select the profile to switch to. Each profile is a card showing the profile's
label and description, with a background color and border that is highlighted on mouseover to make the selection 
easy and visible. 

- The currently active profile's card must be indicated visually (e.g. with a checkmark icon). 
- The default profile must always be the first card in the list.
- Custom profiles are sorted alphabetically after the default profile.
- Paging is not necessary, as the number of profiles is expected to be low (6 is already considered high).
- A single click on a profile card selects it and closes the selection window, triggering the profile switching logic.
- No icons are necessary for the profile cards.

### Manage profiles window

This contains a ListView with a list of all available profile labels and a menu bar, with the following features:

- Add a new profile (via button below the list and "File > Add new menu")
- Delete profile (via list item context menu)
- Edit a profile (via double-click on its list entry)
- Copy a profile (via list item context menu), see the "Copying profiles" section for details

> NOTE: The delete and edit options must be disabled for the default profile. It can be copied, however.

### Copying profiles

When copying a profile, a prompt is displayed to enter a new label (which uses the same validation rules as the
profile properties window for the label), so the new profile gets its own unique ID. The description and all related
profile files are copied from the source profile to the new profile.

The manage profiles window is shown afterwards with the updated profiles list.

> NOTE: No changes to the active profile are made when copying a profile.

### Profile properties window: Create or edit a profile

This window contains input elements to enter / edit the profile's editable properties (see the "Profile properties"
section), and buttons to create it / save it, or cancel the operation. The input elements must have validation logic 
to enforce the requirements specified in the "Profile properties" section.

**Reusability:** Much of the functionality of creating and editing profiles being shared, the create and edit 
windows should share the same base. Passing in a mod instance to the window should switch it to edit mode.

On adding or updating a profile, the manage profiles window is shown with the updated profiles list.

#### Validation

Validation of inputs should be done following industry standards. If Material Design has dedicated error display
paradigms, please use those.
