# Load order profiles

Starfield supports playing with different characters, which have separate folders for savegames. 
These characters can (but must not) have different load orders. In fact, my mod manager tool facilitates 
this through the concept of "Profiles". Each profile is a set of mods that is loosely tied to a 
character in Starfield (it is up to the user to select the mod profile matching the character).

This means that the application must support something similar to switch between load orders. 
I think that it makes sense to use the "Profile" terminology as it is already familiar to mod users.

## Implementation guidelines

See the [Implementation Guidelines](../implementation-guidelines.md) document for general guidelines
on implementing features (code behind and UI).

## The Profile System

### Namespaced reference files

Each profile must have its own reference file. To keep things orderly, they should be saved in a `Profiles` 
subfolder of the configured appdata folder. To distinguish between them, the ID of the profile should be used 
in the file name, e.g. `Plugins.{PROFILE_ID}.txt` (see the section "Profile properties" on details regarding 
the profile ID).

When creating a new profile, its reference file is created as a copy of the current `Plugins.txt` file.

> NOTE: The `Profiles` folder must be created automatically if it does not exist.

### Profile properties

- ID
	- Internal
	- Auto-generated (see section "ID generation") 
- Label
	- Required
	- Editable
	- Max. 30 chars
	- Trim whitespace
	- Must be unique (case-insensitive)
- Description
	- Optional
	- Editable
	- Max 500 chars
	- Trim whitespace

> NOTE: Enforcing these validation rules is done by the create / edit profile UI windows.

#### Disallowed labels

- The following labels are disallowed, as they would conflict with the default profile (case insensitive):
  - `Default`

#### Profile ID generation

The ID should be generated by transliterating the label. The resulting ID must be unique. If a generated ID 
already exists, a numeric suffix should be appended to make it unique (e.g. `my-profile`, `my-profile-1`, 
`my-profile-2`, etc.).

- Character set: ASCII
- Word separator: dashes
- Case: lowercase
- Accented characters: replaced with unaccented equivalents

### Profiles Storage

Ideally, profiles should be JSON objects stored in the `profiles` key of the existing application configuration.
These objects should contain the profile properties (see the section "Profile properties"). Other
information (e.g. the reference file name) can be derived from these properties. A dedicated model 
class should be created to represent profiles in the application.

> NOTE: Migrations for existing configurations are not necessary at this time.

### Renaming profiles

Changing the label of a profile must also rename the reference file name, because it contains the profile ID 
which is derived from the label. If the target file name already exists, the rename operation must fail with an
error message, and the edit profile window must remain open.

> NOTE: Case-sensitive renames are not an issue, because the dynamic part of the file name (the ID) is always lowercase.

### Default profile

If no profile exists, a virtual "Default" profile is created automatically. If the user only uses a single character for 
their games and do not need profiles at all, they can do everything with only the default profile.

- The default profile is virtual: It does not have an entry in the profiles storage.
- The default profile's properties are:
  - ID: `default`
  - Label: `Default`
  - Description: `The default profile is always available.`
- The default profile's reference file is `Plugins.default.txt` in the appdata folder.
- The reference file is automatically created as a copy of the current `Plugins.txt` file if it does not exist.
- The default profile cannot be deleted.

### Switching profiles

When a profile is selected:

- The `Plugins.txt` is replaced with the contents of the selected profile's reference file.
- The active profile display in the main window is updated.
- The [periodic change detection](./impl-periodic-change-checking.md) is updated to use the profile's reference file.

A profile may not be selected if the current `Plugins.txt` has open changes (the [diff](./impl-diff-detection-overview.md) 
between the current reference file and `Plugins.txt` has detected differences), so the option to switch profiles must be 
disabled in that case.

## The Profile Management UI

### MVVM Architecture

See [MVVM Architecture Overview](./impl-mvvm-architecture-overview.md) for an overview of the MVVM architecture
used in the application.

### Active profile display

In the main window, the label of the active profile must be visible, possibly as a text label on the right-hand 
side below the menu. Clicking on it should open the "Switch profile" window.

### Profile menu

Switching and managing profiles should be done via a new "Profile" menu item in the main window's menu strip. 
This must have the following sub-items:

- Switch profile > Open profile selection window
- Manage profiles > Open profile management window

### Switch profile window

Window with a card-based view to select the profile to switch to. Each profile is a card showing the profile's
label and description, with a background color and border that is highlighted on mouseover to make the selection 
easy and visible. 

- The currently active profile's card must be indicated visually (e.g. with a checkmark icon). 
- The default profile must always be the first card in the list.
- Custom profiles are sorted alphabetically after the default profile.
- Paging is not necessary, as the number of profiles is expected to be low (6 is already considered high).
- Double-clicking a profile card or selecting it and clicking the "Switch to profile" button switches to that profile.
- No icons are necessary for the profile cards.

### Manage profiles window

This contains a ListView with a list of all available profile labels and a menu bar, with the following features:

- Add a new profile (via button below the list and "File > Add new menu")
- Delete profile (via list item context menu)
- Edit a profile (via double-click on its list entry)

> NOTE: The default profile must be excluded from the list, so it only shows custom profiles.

### Create and edit profile windows

This window contains input elements to enter / edit the profile's editable properties (see the "Profile properties"
section), and buttons to create it / save it, or cancel the operation. The input elements must have validation logic 
to enforce the requirements specified in the "Profile properties" section.

**Reusability:** Much of the functionality of creating and editing profiles being shared, the create and edit 
windows should share the same base. Passing in a mod instance to the window should switch it to edit mode.

On adding or updating a profile, the manage profiles window is shown with the updated profiles list.
